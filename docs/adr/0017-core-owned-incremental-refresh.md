# Core-owned incremental Refresh with full reconciliation fallback

Repeated full Vault reads make explicit Refresh unnecessarily expensive; Core therefore owns a bounded, session-only native filesystem watcher and uses its change hints to reconcile affected files, subtrees and reference availability only when Refresh is requested, independently of Desktop. Notifications can be delayed or lost and do not cover downtime, so the first Refresh after every Core startup, uncertain notifications, Vault identity changes and the next explicit Refresh after one hour use full reconciliation; users may also explicitly request a full Refresh with valid parsing caches retained, while Rebuild always uses the full scope and reparses. Files remain authoritative, unchanged projections retain their actual hash-check timestamps, mutation guards still verify current bytes and identity, and startup or editing never triggers registration or model calls.

Refresh and manual full reconciliation retain missing registrations so transient absence remains inspectable. Explicit Rebuild instead prunes absent old registration entries after successful full enumeration, together with the new projections and Job completion in one transaction. This makes reconstruction reflect current supported files without erasing workflow history or external receipts. Existing unreadable files remain issue entries, root failure aborts publication, and related Drafts are neither deleted nor reassigned; their sources metadata continues to establish associations independently of Source registration IDs.
